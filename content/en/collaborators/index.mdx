## Purpose
This section on purpose addresses a more granular level of detail than the page [Context](/en/context-narrative). The two go hand-in-hand.

This folder is a public, customer-facing description of the key stakeholder types we aim to work with, and serves to enable our target audience members to see themselves in these roles. This is the reference documentation for clarifying:

- Customer types
- Value propositions
- Business model

Prisma comes from the intersection of the fields Regenerative Design (inc. Organisational Development), Distributed Information Systems, and Group Facilitation. By seeing in terms of the intersection of these fields, it was clear to see the potential to better represent and resource locally-grounded systems-change efforts. See [here](/en/context-narrative/origin-story) for more about Prisma's origins.

## Core Value-adding Process
Prisma's core value-adding process is to create the means for organisational development to take place and to make that visible.

We do this with two key capabilities:

1. **Organising.** Facilitating emergent and aligned collective action.
2. **Publishing.** Using digital infrastructure to generate data from within the organising process. 

> As a second order of capability, our core value-adding process extends to essentialising the means through which to make visible instances of organisational development _repeatably_. We are working on this by developing a common and interoperable accounting substrate - i.e. by developing a protocol.

This is also the place to introduce two foundational concepts, which correspond with _how_ we work on that value-adding process:

1. [Event-organising pattern](/en/processes): Four core processes that represent one version of a minimum viable organising capacity required to design and deliver an event (an intervention unlocking new organisational capabilities).
2. [Publishing stack](/en/patterns/case-study): Minimum viable digital tooling to make organisational development visible from multiple levels of data abstraction, in order to be able to facilitate a developmental learning experience of the systems being worked on.

## Values System
Who pays for this value? And why? This section clarifies our target customers, the partners we want to collaborate with, and how all stakeholder types fit together as part of one system of value.

### Customers
**Origin.** The [origin](/en/context-narrative/origin-story) of Prisma makes clear the original concept was developed within the context of a network going through an organisational transition. This network (of regenerative practitioners) can broadly be characterised as being within the field of Ecological Transition work (sustainability, community resilience etc.). Both together highlight a key theme, which is that Prisma as a system has been designed in service to large-scale, purpose-oriented transition initiatives. This is the same kind of context for our second client, Wada, who were also going through an organisational transition, moving toward a higher order of capability (to be able to apprehend of themselves and act upon opportunities as one network). 

**Generalising.** There are three customer profiles with wants and needs we can service with the same capabilities developed so far.

1. Organisations going through a transition. This includes: digital transformation; and technology adoption requiring behavioural changes. This can be thought of as "organisational development happening to us."
2. Organisations delivering transition-work and/or capacity development. This includes: ecological transition programmes; service design; and social innovation. This can be thought of as "organisational development we do to others."
3. Frontier organisational design. This includes: teal, sociocratic, and holonic organisations; and high-performance teams. This can be thought of as "we _are_ organisational development."

**Essentialising.** Reading across these customer archetypes, it is clear to see we need either one of the following two characteristics to be present in order for us to create value for our target customers:

1. The customer is a complex organisation requiring specialist organising capacity in order to create the conditions required for the next stage of their growth. A good example of this is a multi-level network employing decentralised governance practices (e.g. Wada).
2. The customer works on complex systems/ the way they create value for others is complex. These types of organisations require non-conventional reporting and operational infrastructure in order to be able to communicate the value of their work - in order to be able to see a system's development, not just volumes of transactions/ individual units.

> "Anyone who needs/ wants to generate organisational intelligence within themselves or those they're working with/ on."

This is the foundational building block of our value narrative, from which we then translate into the context of our customers.

**Why pay?** "What's in it for me?"

1. Development happening to us. Prisma delivers development - a generative intervention, sold as an event. The customer pays us for new organisational capabilities. They move from one level of capability to another.
2. Development we do to others. Prisma enhances the customer's existing value propositions - e.g. with visibility. We enable them to make more of the value created by their services visible, by delivering distributed accounting and adoption. The customer pays us to make their work financeable.
3. We are organisational development. This is more likely to take shape on a case-by-case basis as a partnership and/ or integration.

> All of this value narrative is happening on the level of one individual event (one intervention). None of this value narrative requires niether communicates the protocol.

### Partners
Put simply, anyone who can contribute to the capabilities needed to effectively make organisational development visible. That falls into the same two groups as highlighted in the section **Core Value-adding Process** above.

1. **Organising.** Facilitation, systems-change practices, intervention design.
2. **Publishing.** Integrations, data engineering and analytics, infrastructure (inc. hardware - i.e. servers).

> Note, event budget partitioning is structured to be able to dynamically adapt depending on the fulfillment of these capabilities by partners.

### All Stakeholder Types
One event creates value for all participating stakeholders, each with their own incentive to make the event as generative as it can be, all part of one interconnected value system.

In order to complete the set of stakeholder types we tend to work with, we first need to ground all of this work in one of the first principles of Prisma: all systems are nested. This is to say that in order to start organising an event we must first ask where this event is taking place. In this way, the networks we work with must always be regionally grounded by local hubs or local centres of activity.

The next stakeholder type is therefore regional Hubs and, more generally, local communities. The final stakeholder type is the individual participant, which can be any individual.
